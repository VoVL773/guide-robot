## 1. 项目概述与业务闭环

### 1.1 目标

让机器人以自然语音接待访客，并把访客带到场馆内的指定地点；到点后播报、询问是否还需要服务，访客说“没事了”就自动回到待命点。全程受底盘健康、定位状态、前向防撞三层保护。

### 1.2 三个核心场景

| 访客说 | 机器人行为 | 系统动作 |
|---|---|---|
| “带我去跆拳道馆” | “好的，我这就带你去跆拳道馆” | 解析地点 → 规划逐点路线 → 逐段导航 → 到点播报 |
| “现在还有什么事吗” | 自然闲聊（千问） | 调用本地大模型，播报回复 |
| “没事了 / 回去吧” | “好的，我已经回到乐知院待命” | 导航回 `standby` 待命点 |

### 1.3 端到端流程

```text
启动 guide_voice
  └─ 加载 places.yaml，读取底盘地图点位
  └─ 启动自检：定位检查 → 必要时重定位 → 回待命点
       │
       ▼
听取输入（平台 ASR / 本地麦克风 / 文本话题）
       │
       ▼
意图判定（规则优先，大模型兜底）
       ├─ 地点 + 去/到/回 → 导航
       ├─ 只表达意愿      → 询问“需要我带你去吗？”
       ├─ 已在目的地 + “没事了” → 回待命点
       └─ 其他            → 千问闲聊
       │
       ▼
导航执行（规划 → 逐段门控 → 下发 → 轮询 → 到点校验）
       │
       ▼
播报到达话术，等待下一条指令
```

## 2. 能力范围与边界

### 2.1 范围内

- 中文语音识别（本地 Whisper）、平台 ASR 文本接入、文本话题调试；
- 地点别名解析、隐式意图理解、多轮确认；
- 按物理顺序逐点导航，去程/回程不跳点；
- 启动自动重定位、回待命点；
- 三层保护：DTC 健康、定位门控、深度前向防撞；
- 到达播报、到点询问、返回待命点；
- 只读监测看板 + 4 个需显式确认的控制接口。

### 2.2 范围外

- 底盘 SLAM 建图、定位算法、地图编辑器；
- 平台级 TTS / ASR 服务本身；
- 消防巡检业务；
- 多目的地连续任务队列（一次只处理一个目标）；
- 复杂多意图（“先去厕所再去跆拳道馆”）。

### 2.3 关键边界提醒

- 底盘自带 AEB 在自主导航中不生效，安全性依赖本项目的深度防撞；深度相机被遮挡会失去这层保护；
- 定位依赖底盘激光 SLAM，长走廊尽头、玻璃/反光区域置信度会下降；
- 限速是底盘全局参数，修改后手动驾驶同样生效；
- 点位坐标不在本工程维护，底盘 POI 服务端是唯一真源。

## 3. 系统架构与调用链

### 3.1 分层架构

```text
输入层
  ├─ /audio_asr/iat（平台 ASR，需唤醒词）
  ├─ /lyre/audio_stream（本地麦克风，VAD + Whisper）
  └─ /guide_voice/chat（文本调试）
        │
        ▼
决策层  VoiceChatNode（单工作线程串行）
  ├─ PlaceBook：别名、主线、支线、待命点
  ├─ QwenClient：闲聊、隐式意图、到达文案
  └─ 会话状态机：idle / navigating / pending / awaiting
        │
        ▼
执行层  Navigator
  ├─ 路线规划（主线投影、逐点、可反向）
  ├─ 三层门控（健康 / 定位 / 健康复查）
  ├─ 逐段下发 move_to + 状态轮询
  └─ 到点校验、重试、取消确认、AEB、限速
        │
        ▼
设备层
  ├─ Knewbot 底盘 REST（定位 / POI / 动作 / 健康 / AEB）
  ├─ 头部深度相机（前向防撞）
  └─ TTS 服务（播报）

旁路：web_monitor（监测看板，不在控制链路内）
```

依赖方向严格单向：输入层 → 决策层 → 执行层 → 设备层。配置 `places.yaml` 从外部注入执行层，代码中没有硬编码点位坐标。

### 3.2 模块职责

| 模块 | 职责 | 关键点 |
|---|---|---|
| `voice_chat_node.py` | 订阅语音/文本、意图判定、调用导航、播报、启动自检 | 单工作线程，导航中丢弃新语音 |
| `mic_asr.py` | 96 kHz 音频 → 重采样 → VAD 断句 → Whisper 识别 | 热词、初始提示、幻听过滤、播报时闭麦 |
| `qwen.py` | 闲聊、隐式地点意图 JSON、到达文案 | 必须关闭 thinking，否则 content 为空 |
| `places.py` | 别名规范化、地图点位过滤、主支线解析 | 点位必须存在于底盘地图才生效 |
| `navigation.py` | 规划、逐段下发、轮询、恢复、取消 | 所有失败都有明确返回码，不盲目重发 |
| `front_guard.py` | 深度图中央 ROI，p5 距离 + 无效像素占比 | 连续 3 次确认才停车 |

### 3.3 一次导览的调用链

```text
ASR / 文本
  → VoiceChatNode._on_asr / _on_chat / _on_mic_text
    → 过滤、去重 → self._queue
      → _worker_loop（单线程）
        → _handle(text)
          ├─ PlaceBook.resolve(text)        取点位名与播报名
          ├─ _explicit_go(text)             是否含“去/到/回”等动词
          ├─ QwenClient.one_shot            隐式意图 / 到达文案
          └─ Navigator.check_ready()        定位可恢复 + 健康 + AEB
             → Navigator.go(poi, 180s, guard)
               → plan_route()               生成 Leg(name, x, y, yaw) 列表
               → 每段：健康 → 定位 → 健康 → move_to → 轮询 → 到点校验
             → _speak(到达文案 / 失败话术)
```

### 3.4 线程与并发

| 线程 | 职责 |
|---|---|
| ROS executor（单线程） | 订阅回调、服务调用回调 |
| `_worker_loop` | 串行处理所有用户输入，避免并发导航 |
| MicAsr `_loop` | 音频断句与识别，不阻塞 ROS 回调 |
| `_startup_relocalize` | 启动重定位，失败不影响聊天 |

并发约束：

- 导航期间 `_navigating=True`，新的语音/文本直接丢弃；
- 播报期间麦克风 `hold`，避免机器人听见自己的声音；
- 语音、导航、头部服务端各自有互斥，编排层是唯一调用方。

## 4. 关键实现

### 4.1 语音获取与转文字

#### 4.1.1 三条输入通道

| 通道 | 话题 | 消息类型 | 说明 |
|---|---|---|---|
| 平台 ASR | `/audio_asr/iat` | `lyre_msgs/AsrIat` | 平台已完成识别，通常需要唤醒词 |
| 本地麦克风 | `/lyre/audio_stream` | `lyre_msgs/AudioFrame` | 节点启动后调用 `/lyre/audio_control` 打开原始音频流 |
| 文本调试 | `/guide_voice/chat` | `std_msgs/String` | 无麦克风时用于测试 |

#### 4.1.2 本地麦克风链路

```text
/lyre/audio_stream (AudioFrame, int16 PCM)
  → _on_frame：bytes → np.int16，放入队列（maxsize=800）
  → _loop（独立线程）
      → _resample：96 kHz → 16 kHz（整数倍 6:1 均值抽取）
      → 按 10 ms 分块（16 kHz 下 160 点）计算 RMS
      → 能量 VAD 断句
      → _emit：faster-whisper 识别
      → 分段过滤 + 幻听过滤
      → _on_mic_text → 工作队列
  → _handle：进入意图判定
```

源码位置：`guide_voice/mic_asr.py:124-205`（采集、重采样、VAD）、`221-260`（识别与过滤）。

**为什么固定按 96 kHz 处理**：`AudioFrame.sample_rate` 字段不可信，实测写 16000 但实际接近 96 kHz。代码不读消息里的采样率，而是按参数 `mic_rate_in=96000` 重采样到 `rate_out=16000`（`mic_asr.py:1-7` 的模块说明也记录了这一现象）。

#### 4.1.3 VAD 断句规则

| 参数 | 默认值 | 作用 |
|---|---|---|
| `mic_rate_in` | 96000 | 输入采样率，不依赖消息字段 |
| `rate_out` | 16000 | 识别采样率 |
| 分块长度 | 160 点 | 16 kHz 下 10 ms |
| `vad_threshold` | 600.0 | int16 域 RMS 能量阈值 |
| 预录时长 | 0.3 s | 触发前保留，避免吃掉第一个字 |
| `vad_silence_s` | 0.8 s | 连续静音超过该值即断句 |
| `min_speech_s` | 0.4 s | 有效语音不足则丢弃 |
| `max_speech_s` | 12.0 s | 单句上限，防止一直不断句 |
| 队列上限 | 800 帧 | 满后丢弃新帧，避免内存增长 |

断句逻辑（`mic_asr.py:138-188`）：

1. 未激活时持续维护 0.3 s 预录环形缓冲；
2. RMS ≥ 阈值即进入激活态，把预录缓冲作为句首；
3. 激活后持续累积音频，同时统计连续静音块数；
4. 满足“静音 ≥ 0.8 s”或“总长 ≥ 12 s”即封句；
5. 有效语音长度（总长减去静音）≥ 0.4 s 才送去识别。

#### 4.1.4 识别参数

| 参数 | 默认值 | 说明 |
|---|---|---|
| `asr_model` | `small` | faster-whisper 模型 |
| `asr_compute_type` | `int8` | CPU 推理 |
| `asr_language` | `zh` | 中文 |
| `asr_beam_size` | 5 | 束搜索宽度 |
| `asr_hotwords` | 乐知院、核心跑酷、创想谷、厕所、跆拳道馆等 | 提升地名识别率 |
| `asr_initial_prompt` | 一段导览场景提示 | 约束输出风格与常见说法 |
| `no_speech_threshold` | 0.6 | 分段“非语音”概率上限 |
| `log_prob_threshold` | -1.2 | 分段平均对数概率下限 |
| `vad_filter` | false | 已自带能量 VAD，避免二次切分 |
| `condition_on_previous_text` | false | 防止上一句污染当前句 |

#### 4.1.5 识别结果过滤

三层过滤，任何一层命中都直接丢弃：

1. **空文本**：没有内容不进入对话；
2. **固定幻听词**：`谢谢观看`、`请不吝点赞`、`字幕由`、`字幕提供`、`明镜与点点`；
3. **热词整段吐出**：静音或噪声时 Whisper 可能把热词表当文本输出。规则是“命中 ≥3 个热词且 ≥2 个顿号”，或“命中 ≥5 个热词”即判定为幻听（`mic_asr.py:33-47`）。

分段级还会再检查一次 `no_speech_prob` 与 `avg_logprob`，避免把静音段拼进结果。

#### 4.1.6 平台 ASR 通道

`_on_asr`（`voice_chat_node.py:239-252`）处理流程：

1. 取 `msg.text` 并去掉首尾空白；
2. `_meaningful` 过滤空串、纯标点和少于 `min_chars=2` 个有效字符的输入；
3. 导航中直接丢弃；
4. 2 秒内相同文本去重；
5. 放入工作队列。

本地麦克风路径（`_on_mic_text`）与文本话题（`_on_chat`）走相同的过滤与入队逻辑，区别是本地路径没有额外的 2 秒去重（ASR 层已经做过幻听过滤）。

#### 4.1.7 防自听与播报互锁

- `_speak` 下发 TTS 前调用 `_hold_mic(True)`，MicAsr 进入静音态并清空预录、当前句和计数；
- 通过 `TtsService.query` 轮询播放状态，估算时长 `max(1.5, 字数×0.22)`，上限 40 秒；
- 播放结束（或从未进入播放态且超过估算时长+3 秒）后解除静音，并清空静音期间积压的音频帧；
- 这样不会把机器人自己的播报再识别一遍。

#### 4.1.8 降级策略

| 异常 | 行为 |
|---|---|
| Whisper 模型加载失败 | 只停用本地麦克风识别，平台 ASR 与文本通道仍可用 |
| 音频控制服务未就绪 | 打印告警，不影响节点启动 |
| 单句识别异常 | 丢弃该句，继续处理下一句 |
| 麦克风关闭 (`enable_mic=false`) | 只接受平台 ASR 与文本话题 |

### 4.2 大模型理解与任务点对接

#### 4.2.1 设计原则：规则优先、模型兜底、白名单约束

这是本项目 safety 设计的核心，交付时需要明确：

> **大模型不输出坐标、不输出动作、不直接控制底盘。** 它只负责“把自然语言收敛成一个白名单内的地点名”或“生成一句口语回复”，真正的点位解析、路径规划和运动下发全部由确定性代码完成。

原因：

- 底盘运动不可回滚，不能让模型生成任意指令；
- 地点名必须存在于底盘地图，模型幻觉可以被白名单直接拦截；
- 规则可离线工作，模型服务不可用时导航仍然可用。

#### 4.2.2 地点白名单与配置

`config/places.yaml` 只描述“叫什么、按什么顺序走”，坐标全部来自底盘 `GET /api/core/navigation/v1/poi`：

```yaml
standby: 乐知院

aliases:
  乐知院: 乐知教育
  1号点: 乐知教育
  核心跑酷: 核心力量跑酷
  2号点: 核心力量跑酷
  厕所: 厕所
  卫生间: 厕所
  洗手间: 厕所
  3号点: 厕所
  跆拳道馆: 跆拳道馆
  跆拳道: 跆拳道馆
  4号点: 跆拳道馆
  创想谷: 创想谷
  5号点: 创想谷

transfer_points:
  - start_point

main_line:
  - 乐知教育
  - 核心力量跑酷
  - 创想谷
  - 厕所
  - 跆拳道馆
```

`PlaceBook` 初始化时（`places.py:31-86`）：

1. 读取底盘返回的全部点位名，作为“真实存在”的集合；
2. 为编号点位自动生成别名：`3号点`、`3号位置`、`3号位`、`3号`、`点位3`、`第3个点`、`三号点` 等；
3. 配置里的别名只有在目标点位存在于当前地图时才生效；不同地图点位名不一致时，别名可以配置多个候选，取当前地图存在的那个；
4. `transfer_points` 中的点位只参与路线，不出现在可去清单；
5. 配了中文别名的点位，对外统一用中文名播报；
6. `standby` 也通过同一套别名解析。

给大模型看的清单由 `describe()` 生成（`places.py:118-121`），格式为“中文名（点位名）”，例如：

```text
乐知院（乐知教育）、核心跑酷（核心力量跑酷）、厕所（厕所）、跆拳道馆（跆拳道馆）、创想谷（创想谷）
```

#### 4.2.3 三级意图判定

`_handle`（`voice_chat_node.py:288-335`）按以下顺序判定，前一级命中就不再进入下一级：

**第一级：规则命中（确定性，不调用模型）**

- `PlaceBook.resolve(text)`：先去掉空格和标点、转小写，再在整句中寻找**最长匹配**的别名；
- 命中地点且句中包含 `去 / 到 / 前往 / 带我去 / 领我去 / 回 / 走` → 直接导航；
- 命中地点但没有动词 → 记为 `_pending`，播报“可以去某地，需要我带你去吗？”；
- 例如“带我去跆拳道馆”直接导航；“我想练跆拳道”会命中别名“跆拳道”，先询问是否带路。

**第二级：模型推断隐式地点（仅在规则未命中时）**

- 只有当句子包含 `想 / 要 / 去 / 打 / 玩 / 练 / 参观 / 逛 / 看 / 找` 等意愿词时才调用模型（`voice_chat_node.py:337-367`）；
- 提示词要求模型只从白名单里选，没把握就留空，只输出 JSON：

```json
{"selected": "地点名或空字符串", "reply": "一句口语回复"}
```

- 代码用正则提取 JSON，再用 `PlaceBook.resolve(selected)` 做二次校验；
- 校验失败（模型编造地点、返回空、格式错误）就当作普通聊天，不会导航；
- 例如“我想找个地方活动一下”这类没有直接地名的表达，可能被推断为“核心力量跑酷”，但最终仍以白名单校验为准。

**第三级：自由闲聊**

- 交给 `QwenClient.chat`，带 6 轮历史，回答限一到三句口语；
- 模型不可用时播报固定兜底话术“我这边暂时联系不上大模型，请稍后再试”。

#### 4.2.4 从话术到任务点的完整映射

```text
用户话术
  → 别名匹配（places.yaml）
    → 地图点位名（例如 跆拳道馆）
      → 底盘 POI 坐标（GET /api/core/navigation/v1/poi，首次读取后缓存）
        → plan_route() 生成 Leg(name, x, y, yaw)
          → move_to(x, y, yaw)
```

关键点：

- 代码里没有 `POI_xx` 常量，也没有任何坐标；
- 换地图后，旧点位自动失效，不会拿错误坐标去跑；
- 地图上不存在的目标会被 `go()` 直接拒绝并返回失败，不会盲走。

#### 4.2.5 会话状态机

```text
                 ┌──────────────────────────────┐
                 ▼                              │
  ┌────────┐  地点+动词   ┌────────────┐  到达   ┌──────────┐
  │  idle  │────────────▶│ navigating │───────▶│ awaiting │
  └────────┘             └────────────┘        └──────────┘
      │ 地点无语义动词             ▲                  │
      ▼                            │                  │ “没事了/回去吧”
  ┌────────┐   肯定（好/需要/可以）│                  │
  │ pending│───────────────────────┘                  │
  └────────┘                                          │
      │ 否定（不用/算了/先不）                          │
      ▼                                                ▼
   结束本轮                                      导航回 standby
```

实现细节：

- `_navigating` 为真时，任何新输入都丢弃，避免半路改目标；
- `_navigate` 开始前清空队列，防止导航中积累的旧语音在结束后被误执行；
- `_pending` 只在下一轮有效，命中否定词直接取消；
- `_awaiting` 表示“已把访客送到目的地”，此时听到 `没事 / 没有了 / 不用了 / 没有别的 / 没别的 / 就这样 / 结束 / 回去` 就回待命点；
- 到达后如果听到其他内容，仍走正常意图判定或闲聊。

#### 4.2.6 大模型调用参数

| 参数 | 默认值 | 说明 |
|---|---|---|
| `qwen_base_url` | `http://120.48.75.178:7006/v1` | vLLM 的 OpenAI 兼容接口 |
| `qwen_model` | `Qwen3.5-122B-A10B` | 本地部署模型 |
| `qwen_timeout` | 30 s | 单次请求超时 |
| `history_turns` | 6 | 保留最近 6 轮对话 |
| `temperature` | 0.6 | 代码内固定 |
| `max_tokens` | 300 | 代码内固定 |
| `enable_thinking` | false | **必须显式关闭** |

`enable_thinking=false` 的原因：该服务是 Qwen3 系列，开启思考时 `content` 会返回 `null`，token 全部被 reasoning 内容占用，表现为“模型返回空内容”。`qwen.py:58-65` 已在每次请求中显式关闭。

#### 4.2.7 为什么不让大模型直接“拆分任务”

交付时需要说明这个取舍：

- **可控**：模型只做语言归一化，输出空间被压缩到“白名单地点名 + 一句话”，不会出现“移动到某坐标”这类不可审计指令；
- **可测**：47 项单元测试全部使用假底盘，规则路径不依赖模型服务；
- **可降级**：模型超时或断网时，明确的“带我去某地”仍然可用；
- **防幻觉**：模型给的地点必须能在地图点位中找到，否则直接忽略。

### 4.3 导航流程实现

导航核心在 `navigation.py`，对外只有两个入口：`check_ready()` 和 `go()`。`go()` 返回明确字符串，不抛业务异常。

#### 4.3.1 基本数据结构

```python
Leg = namedtuple("Leg", "name x y yaw")
```

- `name`：本段目标点位名；
- `x, y`：目标坐标（来自底盘 POI）；
- `yaw`：本段行进朝向，由前一点到当前点的方向计算，**不使用 POI 自带的 yaw**（POI 里通常统一为 0，不能代表返程方向）。

#### 4.3.2 路线规划（plan_route）

源码：`navigation.py:250-359`。

1. 读取当前位姿，取 `(x, y)`；
2. 若没有配置主线、目标不在主线/支线、或读不到位姿 → 直接生成一条到目标的 Leg；
3. 若当前在支线上（离支线点比离挂接点更近）→ 先回挂接点，再走主线；
4. 否则把当前位置**投影到主线的折线上**：
   - 对每一段计算投影参数 `t`（限制在 0~1）和点到线段的距离；
   - 取距离最小的段，得到 `position = 段下标 + t`；
5. 方向判定：
   - `target_index >= position`：`ceil(position)` 开始，正向逐点；
   - `target_index < position`：`floor(position)` 开始，反向逐点；
6. 把当前点、途经点、目标点串成点列，逐段计算 `yaw = atan2(dy, dx)`；
7. 长度小于 `0.15 m` 的段直接跳过（已经站在点上）。

**示例**：主线为 `乐知教育(0) → 核心力量跑酷(1) → 创想谷(2) → 厕所(3) → 跆拳道馆(4)`，当前位置在 0 到 1 之间 40% 处：

| 目标 | position | 起始下标 | 途经点 |
|---|---|---|---|
| 跆拳道馆 | 0.4 | ceil = 1 | 核心力量跑酷 → 创想谷 → 厕所 → 跆拳道馆 |
| 乐知教育 | 0.4 | floor = 0 | 乐知教育 |

这条规则保证：

- 去程、回程都逐点经过，不跳点；
- 中途恢复时，投影点在前方也不会被误判为“已到达”；
- 不会因为抄近路而漏掉拐角或必经点。

#### 4.3.3 go() 主流程

源码：`navigation.py:712-780`。

```text
go(poi, timeout=180s, guard)
  ├─ 检查是否有未确认的取消 → 有则先取消确认，否则返回 network
  ├─ 读取点位列表（失败重试一次）
  ├─ 目标不在点位列表 → failure
  ├─ 出发前防撞预检
  │    ├─ 上次被防撞取消过，或当前正前方有障碍
  │    └─ 要求前方连续清空 1.5s（最多等 10s），否则返回 blocked
  ├─ 健康检查（允许定位恢复）
  ├─ 定位门控（最长等到 deadline）
  ├─ 健康复查（防止恢复等待期间出现新故障）
  ├─ 打开 AEB
  ├─ 下发限速（默认 0.6 m/s，失败只告警）
  ├─ 轨道模式（track_id != 0 且目标不是支线）→ 原生轨道导航
  └─ 否则 plan_route() → 逐段 _navigate_leg()
       └─ 每段结束后停 1.0s，让底盘停稳再发下一段
finally:
  └─ 取消确认成功 → 关闭 AEB
     取消未确认 → 保留 AEB，并禁止新的导航任务
```

#### 4.3.4 单段导航（_navigate_leg）

源码：`navigation.py:808-834`。

每一段最多尝试 3 次，每次下发前完整执行三道门控：

```text
for attempt in 1..3:
    ├─ 健康检查（A/B 类故障阻断）
    ├─ 定位门控（连续稳定 3 秒）
    ├─ 健康复查
    ├─ _dispatch()：move_to(x, y, yaw, flags=0)
    └─ _run_action()：轮询到终态
         ├─ success → 返回
         ├─ blocked → 立即返回，交给上层等待/重试
         ├─ timeout / localization / network → 立即返回
         └─ failure → 进入下一次尝试（先等 1.5s）
连续 3 次失败 → failure
```

#### 4.3.5 定位门控

源码：`navigation.py:594-661`、`836-869`。

- 要求 `slam_status == 0` 且位姿 `confidence > 0` **连续保持 3 秒**；
- 先去等 8 秒自然恢复，避免底盘短暂抖动就打断；
- 未恢复且状态为 1/2/3/5 时，最多主动重定位一次：
  - 初值优先吸附 3 m 内的已知点位坐标；
  - 其次使用近期可信位姿（非空闲状态允许最近 1 小时，空闲状态只允许 90 秒）；
  - 没有可信初值就拒绝盲目重定位；
- 原地重定位不收敛时，重新加载当前地图再启动定位；
- 状态 4（空闲）不会自行恢复，直接重新加载地图启动定位，30 秒冷却；
- 状态 6/7/8 表示底盘正在恢复，只等待，不重复打断。

| slam_status | 含义 | 动作 |
|---|---|---|
| 0 | 正常 | 放行 |
| 1/2/3/5 | 丢失/降级/异常/等待重定位 | 等待，必要时主动重定位一次 |
| 4 | 空闲（定位服务未启动） | 重新加载当前地图并启动定位 |
| 6/7/8 | 底盘正在恢复 | 只等待 |

行驶中的额外规则：定位异常持续 8 秒，但剩余距离仍在减少（≥0.3 m）→ 继续任务；没有前进才取消本段。

#### 4.3.6 健康检查

源码：`navigation.py:875-923`。

- 逐条解析 DTC 的 `severity`：
  - A 类 / B 类 / `FATAL` / `ERROR` → 阻断；
  - C 类（例如 WiFi 未连接）→ 只告警；
  - 没有 `severity` 字段的老固件 → 保守视为阻断；
- `hasFatal/hasError` 是聚合标志，一条 C 类告警也会置真，所以不能只看聚合标志；
- 特例 `0x03020003`（定位置信度低）：只在“恢复等待入口”暂缓，真正下发运动前仍然阻断；
- 维护模式会给出明确提示：“请先弹起维护按钮，退出手动模式”。

#### 4.3.7 动作下发与轮询

源码：`navigation.py:925-1116`。

下发：

- 使用规划坐标和行进朝向调用 `move_to(x, y, yaw, flags=0)`；
- `flags=0` 表示起步/到点旋转，路径仍由底盘规划；
- 成功返回 `action_id`。

轮询：

- 每 0.2 秒查询一次动作状态；
- 状态归一化为 `success / failure / running`；
- `done` 只说明任务结束，不保证成功，必须结合 `success` 字段判断；
- 查询连续失败 2 次 → 视为网络不确定，退出等待并记录待取消任务；
- 正常运行时每 2 秒打印一次剩余距离、定位状态、置信度。

到点校验（`navigation.py:986-1025`）：

1. 动作报成功后，先等定位连续稳定（最多 20 秒）；
2. 读取位姿，要求 `confidence > 0`；
3. 与目标距离 ≤ `0.35 m` 才算到达；
4. 定位不稳定但距离 ≤ `1.0 m` 时，按到达处理并记录告警；
5. 位姿可信但超过 0.35 m → 判失败，由本段重试机制重新下发；
6. 定位不可信且超过 1.0 m → 返回 `localization`，交由上层播报。

#### 4.3.8 前向防撞

源码：`front_guard.py:43-95`、`navigation.py:948-967`。

- 订阅 `/ob_camera_head/depth/image_raw`，使用传感器 QoS（发布端是 best-effort）；
- 支持 `16UC1`（毫米转米）与 `32FC1`；
- 取画面中央 ROI：横向 35%~65%，纵向 25%~60%；
- 距离取有效像素的 **5% 分位数**，避免个别噪点误触发；
- 停车条件：`p5 < 1.2 m` 或 ROI 内无效/过近像素占比 ≥ 6%；
- 下发后 1.5 秒内不检查，给底盘起步时间；
- 连续 3 次轮询都判定有障碍才取消，防止单帧误判；
- 取消后记录时间，重发前要求前方连续清空 1.5 秒，最多等 10 秒。

上层重试（`voice_chat_node.py:369-415`）：

- 第一次 `blocked` 播报“这边暂时过不去，我先停一下”；
- 等待前方清空，最多 60 秒；
- 清空后播报“路通了，我继续走”，重新调用 `go()`；
- 最多尝试 3 次（含首次，`front_guard_retries`）；重试耗尽后播报失败话术。

#### 4.3.9 超时、重试与取消

| 项 | 值 | 说明 |
|---|---|---|
| 整条路线预算 | 180 s | `nav_timeout`，所有段共享 |
| 单段尝试 | 3 次（含首次） | 每次重发前重新做三道门控 |
| 重发间隔 | 1.5 s | 让底盘从失败态退出 |
| 段间停稳 | 1.0 s | 避免停稳过渡期被瞬拒 |
| 主动重定位 | 每次 `go` 最多 1 次 | 共用路线预算 |
| 定位恢复等待 | 20 s | 原地重定位上限 |
| 取消确认等待 | 2 s | 等动作退出 running，再补一次取消 |
| 请求超时 | 3 s | 底盘 REST 单次上限 |

通信不确定的处理：

- `move_to` PUT 超时视为“可能已接单”，**禁止直接重发**；
- 记录 `_pending_cancel`，恢复通信后先取消并确认，才允许新任务；
- 取消未获确认时保留 AEB，不假设底盘已经停下。

#### 4.3.10 返回码与播报

| 返回码 | 含义 | 播报 |
|---|---|---|
| `success` | 到达 | 送客：模型生成到达话术；回待命：固定待命话术 |
| `blocked` | 前方障碍取消 | “这边暂时过不去，我先停一下” → 等待 → 重试；重试耗尽转为失败话术 |
| `network` | 通信异常/任务状态未知 | “我与底盘的通信异常……不要重复下发导航” |
| `health` | 底盘故障 | 具体故障提示（含维护模式、定位置信度） |
| `localization` | 定位持续不稳定 | “我现在定位持续不稳定，先停在这里……” |
| `failure` | 底盘任务失败/到点校验失败 | “抱歉，这次没能到某地……” |
| `timeout` | 整条路线超时 | 同上 |

### 4.4 播报实现

- 服务：`/intelligent_interaction/tts/play`（`interaction_msgs/TtsService`）；
- 调用 `append` 下发文本，`type=text`，`audio_id=audio_guide`；
- `audio_id` 必须是 `audio_config.json` 中开启 stop 权限的文本实体，否则取消无法真正打断音频；
- 服务未就绪时只告警，不阻断导航；
- 播报期间闭麦，播完恢复（见 4.1.7）；
- 到达文案由模型生成，模型失败时使用固定话术。

### 4.5 启动自检

源码：`voice_chat_node.py:169-200`。

1. 读取定位状态；
2. 状态 4（空闲）时先尝试重新加载地图并启动定位；
3. 以待命点坐标重定位（`relocalize_timeout` 默认 20 秒）；
4. 重定位成功后，若 `startup_goto_standby=true`，先导航回待命点；
5. 任一步失败只告警，不阻止聊天功能。

### 4.6 监测平台（web_monitor）

#### 4.6.1 定位与设计边界

`web_monitor` 是机器人本机的独立 Web 工作台，用于现场值守、演示和排障。它与导览、导航、相机、底盘进程完全独立，不改动这些程序、配置或启动项。

明确的边界：

- 不参与导航决策，不直接调用底盘 SDK；
- 不新增状态话题，任务状态由 `guide_voice` 的日志解析得到；
- 只向 `/guide_voice/chat` 发布文本，不直接发布速度、位姿或底盘指令；
- 只读访问底盘三个固定接口：电量、位姿、点位；
- 默认监听 `0.0.0.0:8765` 且无登录鉴权，只适合部署在受控局域网。

#### 4.6.4 任务状态识别

页面不额外发布状态话题，而是订阅 `/rosout`，只处理 `guide_voice` 节点的 INFO 日志，用四条正则折叠成任务状态（`monitor.py:74-156`）：

| 日志特征 | 状态变化 |
|---|---|
| `开始定点导航：某地点` | `running`，起点记为“当前位置” |
| `定点导航到 某地点：N 个导航段，A -> B -> ...` | `running`，解析完整路线与途经点 |
| `到达 某地点，用时` | 目标匹配时变为 `done` |
| `连续 N 次导航任务失败 / 未通过到点位置校验 / 定位持续不稳定 / 前方持续有障碍` 等 | `failed` |

任务卡片展示：当前状态、目标地点、路线步骤、途经点完成态、最近更新时间。停止节点时任务复位为 `idle`。

这样做的代价是依赖日志文案；改动 `voice_chat_node.py` 的导航日志格式时，需要同步检查这里的正则。

#### 4.6.5 运行示意图实现

示意图由 `live.js:234-398` 直接生成 SVG（`viewBox 980×372`）：

- 比例 `scale = 22 px/m`，原点 `x0 = -2.5, y0 = 9.9`；
- 画一条主走廊和上下两个分支，三段共用外轮廓，接缝处没有多余墙线；
- 站点顺序完全来自 `places.yaml`，站点坐标来自底盘 `GET /api/core/navigation/v1/poi`；
- 机器人位置取底盘 `pose.x`，只按 X 方向投影到走廊，得到 0~1 的沿线进度；
- 使用绿色胶囊标记位置，浮层显示“任务 N% / 前往某站点”，待命时显示最近站点；
- 位姿超过 5 秒未更新时标记变暗；页面提示该图只表示大致进度，不表示真实几何。

只按 X 投影的原因：主走廊是直线，这样即使定位 y 有轻微漂移，标记也不会被甩出走廊。示意图因此是“状态可视化”，不是“地图渲染”。

`map.png` 与 `map_calib.json` 仍会被加载和提供下载，但当前页面落点不依赖标定换算。

#### 4.6.6 数据来源与刷新频率

| 数据 | 来源 | 频率 | 失效表现 |
|---|---|---|---|
| CPU、温度、内存、开机时长 | 主机 `psutil` 与 `/sys/class/thermal` | 2 s | 显示旧值并标记新鲜度 |
| ROS 节点/话题/服务 | `rclpy` 图查询，不调用服务 | 5 s | 顶部连接状态变为断开 |
| 底盘位姿 | `GET /api/core/navigation/v1/pose` | 1 s | 示意图标记变暗、位姿读数隐藏 |
| 底盘点位 | `GET /api/core/navigation/v1/poi` | 变化时 10 s，否则 30 s | 示意图回退到等距站点 |
| 电量 | `GET /api/core/system/v1/battery/pack` | 5 s | 显示等待电量数据 |
| 彩色画面 | 头部相机话题 | 约 3 帧/s | 画面隐藏并提示等待 |
| 深度画面 | `/ob_camera_head/depth/image_raw` | 约 2 帧/s | 同上 |
| 麦克风活跃 | 只记录 `/lyre/audio_stream` 最后接收时间 | 随消息 | 显示超时 |
| 告警 | `/rosout` 白名单节点 | 最多 1 条/s | 事件流停止新增 |
| 当前任务 | `guide_voice` 导航日志 | 随日志 | 保持上一次状态 |

图像处理约束：彩色图宽度超过 768 px 时等比缩放，JPEG 质量 65；深度图仍按 16UC1/32FC1 解析，并计算中央 ROI 的 p5 距离与无效像素占比。所有画面只存在内存中，不录像、不落盘。

电量只认底盘返回的 `isCharging` 布尔值，不根据电流正负推断充电状态。

#### 4.6.7 HTTP 接口与安全边界

只读接口：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/status` | 主机、ROS 图、采样、相机、任务、点位、节点状态 |
| GET | `/api/logs` | 事件流，最多 200 条，已脱敏 |
| GET | `/api/frame?kind=color\|depth` | 最新 JPEG 帧；超过 3 秒返回 503 |
| GET | `/`、`/index.html`、`/live.js`、`/map.png`、`/schematic_base.png` | 静态白名单文件 |

需要显式确认的控制接口（`POST`，请求体必须含 `{"confirm": true}`）：

| 路径 | 行为 | 拒绝条件 |
|---|---|---|
| `/api/node/start` | `ros2 run guide_voice voice_chat --ros-args -p startup_goto_standby:=false` | 节点已在运行时返回 409 |
| `/api/node/stop` | 只停止本页启动的进程：先 SIGINT，8 秒后 SIGTERM | 非本页启动返回 409 |
| `/api/navigate` | 校验地点在 `places.yaml` 白名单后，发布“去某地点” | 地点非法 400、节点未运行 409、ROS 未就绪 503 |
| `/api/command` | 原文发布到 `/guide_voice/chat`，最长 200 字 | 空内容/超长 400、节点未运行 409 |

统一状态码：缺少确认标记 400，未知路径 404，PUT/PATCH/DELETE 405，重复启动或非托管停止 409，ROS 未就绪 503。

安全措施：

- 静态文件使用固定白名单，不拼接用户路径，不提供任意文件读取；
- 日志写入前对 API Key、Token、密码、`Authorization`、`Bearer` 等字段做脱敏；
- 响应带 `Content-Security-Policy`、`X-Content-Type-Options: nosniff`、`Cache-Control: no-store`；
- 不提供命令执行接口；唯一会启动进程的路径是固定参数的节点启动；
- 页面不直接访问底盘 SDK，只通过监测服务的只读 HTTP 与 ROS 发布。

## 5. 配置与换场馆

### 5.1 配置项说明

| 字段 | 作用 | 约束 |
|---|---|---|
| `standby` | 待命点 | 必须能解析到当前地图点位 |
| `aliases` | 语音别名 → 点位名 | 目标不在当前地图时自动忽略 |
| `main_line` | 主线点位顺序 | **必须按物理顺序排列** |
| `branches` | 支线 → 挂接主线点 | 用于先到挂接点再进支线 |
| `transfer_points` | 只中转、不作为目的地 | 不出现在可去清单 |

### 5.2 换场馆步骤

1. 在底盘或 App 里建点，记录中文点位名；
2. 修改 `places.yaml` 的 `aliases`、`main_line`、`branches`、`standby`；
3. 默认安装配置需先重新构建，再重启语音节点；若使用外部 `places_file`，直接重启。检查启动日志中的“可去地点 / 主线点”是否符合预期；
4. 先短距离单段试跑，再跑完整往返；
5. 如现场点位名变化，同步更新 ASR 热词与初始提示，提升识别率。

### 5.3 配置生效规则

- 别名目标不存在于当前地图 → 该别名被丢弃，不会报错；
- 主线里不存在的点位 → 被过滤；
- 主线为空或目标不在主线 → 直接前往目标点，不做逐点中转；
- 启动时会打印地点数量、待命点、主线点数、支线数，便于现场核对。

| 现象 | 可能原因 | 处置 |

## 9. 已知限制与风险

1. **定位依赖底盘激光 SLAM**：长走廊尽头、玻璃/反光区域置信度会下降；低置信度时系统会停车等待，而不是硬走。
2. **底盘 AEB 在自主导航中不生效**：安全性依赖深度防撞；深度相机被遮挡会失去保护。
3. **限速是全局参数**：修改后手动驾驶同样生效。
4. **单目标**：一次只处理一个目的地，不支持“先去 A 再去 B”。
5. **单轮确认**：地点确认只支持简单肯定/否定，复杂多意图不支持。
6. **模型服务依赖网络**：闲聊和隐式意图依赖千问服务；服务不可用时，明确地点指令仍可执行。
7. **换图需重新建点**：`places.yaml` 必须与新地图点位名一致，否则别名会被过滤。
8. **监测看板无鉴权**：默认面向局域网，部署时需限制网络访问。
